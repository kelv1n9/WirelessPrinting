## 4. Что нашёл и починил по дороге

1. **После потери Wi-Fi облако не возвращалось, и модуль перезагружался.** Порог «45 КБ одним куском» для старта был догадкой: после обрыва было 105 КБ свободно, но наибольшим куском 44.1 КБ. Порог теперь 20 КБ куском и 80 КБ всего.
2. Сторож перезагружал модуль из задачи с малым стеком и терял и строку журнала, и причину. Причина теперь лежит в памяти, которая переживает сброс, строку пишет главный цикл.
3. После переподключения загрузка ждала куски на старом соединении по 20 с на попытку (88 с). Теперь попытка обрывается сразу (42 с).
4. Файл, сжатый с окном больше, чем у модуля, распаковывался в мусор молча. Теперь у потока заголовок zlib и контрольная сумма всего файла, такой файл отклоняется.
5. Заминка карты дольше 3 с теряла кусок файла. Ожидание места поднято до 15 с.
6. Взаимная блокировка: задача сокета ждала место, а запись ждала сокет, чтобы подтвердить. Подтверждения теперь шлёт сама задача сокета.
7. Начало файла выбрасывалось при старте приёма (моя правка этого же вечера, убрана).
8. Цифра свободной памяти считала память кода. Исправлена везде, пороги Telegram пересчитаны.
9. Показания розетки Яндекса перестали читаться после моей же правки памяти. Починено, проверено: `watt 8.7`.
10. **Оборванная загрузка оставляла на карте полфайла,** который выглядел как целый. Теперь удаляется вместе со служебными файлами.
11. Загрузка с именем файла, который в этот момент читается для принтера, перезаписывала его на ходу. Теперь отклоняется.
12. Файл, загруженный во время передачи другого, на принтер не уходил. Теперь очередь.
13. Убран heatshrink из облачного пути: 6 файлов удалено.

14. Очередь держала один файл и стартовала раньше записи в журнал. Теперь до шести файлов, строка о каждом на месте.
15. **Долгая загрузка позади передачи на принтер сбивала её** (принтер бросает передачу после 10 с тишины), спасал один повтор. Передача теперь обслуживается и изнутри загрузки.

## 5. Открытое и честные пределы

- **Предел в 32 gcode-файла на карте принтера.** При 33-м модуль пишет «the printer did not answer with a listing», хотя файл доехал, и печать после загрузки не стартует. Я сам упёрся в него тестовыми файлами (`23:39:43 could not put zz_busy.gcode on the printer's card`). Тестовые файлы с карты принтера удалены, сейчас там только `Calibration_PETG.gcode`, передачи снова отчитываются верно (`23:44:15 zz_check.gcode is on the printer's card`). Сам предел не чинил, ждёт апрува.
- **Облако дважды отваливалось на 17–19 с без обрыва Wi-Fi:** `22:46:18 remote access lost` и `23:28:47 remote access lost, last heard 3 s ago`, оба раза вернулось само. Во второй раз видно, где: Worker в ту же секунду отвечал «модуль не подключён» и закрытия сокета не записал, а модуль слышал его за 3 с до того. Значит сокет пропал на стороне Cloudflare. Из 17–19 с десять это жёсткая пауза библиотеки перед переподключением, её можно обойти.
- После снятия питания посреди загрузки на карте модуля остаётся пустой файл с именем загрузки (0 байт). Принтеру он не уходит.
- Пять замечаний разбора кода с малой вероятностью не исправлены: зависание библиотеки сокета на разорванном кадре, гонка при остановке сокета, пять открытых файлов при пределе четыре (пропадает картинка-превью), порядок проверок в одном редком пути, замер карты.
- На карте модуля остались тестовые файлы zz_*.
- **Карта модуля иногда замирает на 1–5.6 с** (`worst write 5632 ms`, в `/bench/card` до `worst write 4546 ms`). Это сама карта, замерено отдельно от нашего кода: 64 ГБ, кластеры 32 КБ, почти пустая. Из-за этого загрузка иногда идёт 18–24 с вместо 15–16. Можно переформатировать её SD Formatter или поставить другую, по желанию.
- Блоки 8 КБ в замере карты давали то 506–526 КБ/с, то 1405–1459 КБ/с. Стабильно быстро только 16 КБ.
